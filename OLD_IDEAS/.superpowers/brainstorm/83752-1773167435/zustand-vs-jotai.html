Zustand vs Jotai — Deep Comparison

For StellarOS specifically: a 3D canvas + HUD + resource economy + single user

A — Zustand
THE MENTAL MODEL

One store. An object with state + actions. Like a singleton. You call useStore(s => s.selectedNode) from anywhere — canvas or HUD — and it just works. No providers, no atoms.

HOW IT LOOKS IN SOL
// store.ts — one file
const useStore = create((set) => ({
nodes: [],
selectedNode: null,
cogBandwidth: 0,
zoomLevel: 1,
selectNode: (id) =>
set({ selectedNode: id }),
}))
// In R3F canvas — clicks update store
// In HUD sidebar — reads selectedNode
// They stay in sync automatically

Pros for SOL

  • R3F native — useStore() inside useFrame() works perfectly. No React re-renders in the animation loop.
  • Canvas ↔ HUD bridge — clicking a node in 3D → HUD sidebar updates. This is Zustand's strongest use case.
  • Resource economy — bandwidth, resilience, focus all sit in one store. Easy to compute derived values.
  • Simple to reason about — one file, one store, predictable. Good for solo dev.
  • Battle-tested with R3F — used in nearly every complex R3F project (Drei internally, pmndrs ecosystem)

Cons

  • Store can grow large if you put everything in it (split into slices to prevent this)
  • Less granular reactivity — a component re-renders if any subscribed slice changes (mitigated with selectors)
  • Mutations are imperative — feels less "React" than Jotai
BEST FOR SOL WHEN:
You want the 3D canvas and HUD to share state with zero ceremony. Click node → camera flies → sidebar shows detail → resource bar updates. All from one store.
B — Jotai
THE MENTAL MODEL

Atoms. Each piece of state is a tiny independent unit. You compose them — derived atoms compute from base atoms. Like signals or observables. Feels like a reactive spreadsheet.

HOW IT LOOKS IN SOL
// atoms.ts — many small atoms
const nodesAtom = atom([])
const selectedNodeAtom = atom(null)
const zoomLevelAtom = atom(1)
// Derived — auto-recomputes
const cogBandwidthAtom = atom((get) => {
const nodes = get(nodesAtom)
return nodes.reduce(
(acc, n) => acc + n.cost, 0)
})
// Each component subscribes only
// to atoms it cares about

Pros for SOL

  • Surgical re-renders — a component subscribed to selectedNodeAtom only re-renders when that atom changes. Zero waste.
  • Derived atoms shine — cogBandwidth = sum of all node costs. Resilience = composite of sentiments. These compute automatically.
  • Works with R3F — jotai has useAtomValue() which is fine inside components. Less ergonomic inside useFrame() than Zustand.
  • Composable — easy to split concerns cleanly as the app grows

Cons for SOL

  • useFrame() friction — Jotai atoms don't play as cleanly inside R3F's animation loop. Need workarounds (store refs, read atom outside component)
  • More boilerplate — 8 nodes × multiple state atoms = many files. Harder to see the full picture.
  • Less obvious for canvas-HUD bridge — not the primary use case Jotai was designed for
  • More mental overhead for solo dev
BEST FOR SOL WHEN:
You have many independent reactive values and derived computations that change at different rates. Great if the resource economy becomes very complex. Overhead not worth it for Phase 1.
THE KEY DIFFERENCE FOR SOL
Zustand wins at:
Canvas ↔ HUD bridge · useFrame() animation loop · Imperative 3D event handling · "Click node, everything reacts" · Simple mental model for solo dev
Jotai wins at:
Derived resource calculations · Surgical re-renders · Composable reactive state · Apps with many independent state slices that rarely cross-talk
SOL is fundamentally a canvas-HUD bridge problem: you click things in 3D and the HUD reacts. That's Zustand's home turf. The resource economy derivations are doable in Zustand via computed selectors. Jotai would excel if the resource economy were the primary UI, but it's not — the 3D is.
