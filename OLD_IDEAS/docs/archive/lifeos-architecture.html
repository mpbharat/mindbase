LifeOS Architecture

Four layers, strict boundaries. The skin never touches the database. The core never knows what a galaxy is.

3
Skin — Stellaris
The 3D galaxy, shaders, HUD, game feel. Pure presentation. Reads adapter output, renders it as an interactive space scene. Knows nothing about health scores or load values — only about planets, orbits, and glow intensity.

Skin Adapter — Stellaris Translator
The Rosetta Stone. Reads LifeOS core data and translates it into Stellaris concepts. Health becomes stability. Engagement becomes energy. Drives become factions. Computes game-specific derived values (Cognitive Bandwidth, Emotional Resilience) from generic metrics.
Per-skin
mapDomainToPlanet() calcCogBandwidth() calcResilience() calcFocus() mapDrivesToFactions() mapModeToDesignation() mapChallengeToSituation() mapInterventionToEdict()
This layer owns: Terminology mapping, game-specific formula computation, Stellaris-specific derived metrics. Each skin gets its own adapter.
Input LifeOS core types (Domain, Item, Challenge, Drive)
Output Stellaris types (Planet, Situation, Faction, Edict)
Key rule Pure functions only. No side effects. No DB writes. Stateless transform.
Example domain.health:72 → planet.stability:72 + "Stable" label + green glow hint

LifeOS Core — Engine
The truth layer. Domain graph, items, metrics, challenges, drives, complexity, people, events. All business logic lives here. Computes health scores, detects drift, ticks challenges, captures snapshots. Exposes everything via REST API. Knows nothing about visualization.
Universal
Domain Graph Items / Tasks 5 Core Metrics Progressive Challenges Internal Drives Complexity Score Interventions People Health Signals Activity Log Attention Log Learning Log Life Events Snapshots Seasonal Rhythms REST API
This layer owns: All business logic, all data models, all computations. The single source of truth.
Tech Next.js API routes, Drizzle ORM, pure computation functions
Exposes REST API — GET /api/state, POST /api/activity, etc.
Never does Render anything. Reference any skin concept. Know about 3D, shaders, colors.
Key test If you deleted all skins, could you still curl the API and manage your life? Yes.

Data Layer — Neon Postgres
The persistent store. Skin-agnostic schema. No column is named "stability" or "bandwidth" — those are adapter-level translations. Tables store domains, items, activities, challenges, people, events, snapshots.
Persistent
domains items activity_log challenges drives people interactions health_logs learning_log attention_log life_events snapshots seasonal_rhythms connections interventions
This layer owns: Persistence. Schema. Migrations. Nothing else.
Tech Neon Serverless Postgres 17
Schema rule Generic column names only. health not stability. engagement not energy.
Access Only via LifeOS Core layer (never direct from skin)

Same data, different language. The adapter is a pure function — LifeOS in, Stellaris out.
